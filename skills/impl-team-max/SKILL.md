# impl-team-max

Contract-First アプローチでインターフェースを事前定義し、複数開発者がスコープごとに安全な並列開発を実現する。

> **注意**: Agent Teams を使用するため `impl-max` より多くのトークンを消費する。並列化のメリットが少ない小規模タスクには `impl-max` を推奨。

## 前提条件

- Claude Code 環境
- `git`, `gh` CLI

## 引数

`impl-max` と同じ:
- **Issue 番号** / **Issue URL** / **テキスト** / **引数なし**

## フェーズ1: 要件分析とスコープ分割

`impl-max` のフェーズ1と同じ手順で要件取得・ブランチ作成（命名は `impl-max` の `references/branch-naming.md` 参照）。

スコープ分割時の注意：
- **ファイル所有権の分離**: 各スコープの編集ファイルが重複しないよう分割
- 同ファイルを複数開発者が編集する場合は1つのスコープにまとめる
- 並列実行可能なスコープを最大化する

## フェーズ2: Contract-First 定義

開発者スポーン前に共有インターフェースを定義してコミット：
- 型定義 / インターフェース
- 関数シグネチャ
- API エンドポイントの形
- データモデルスキーマ

**契約定義をコミットしてから次のフェーズに進む。**

## フェーズ3: チーム編成と並列実装

1. エージェントチームを作成
2. チームメイトをスポーン:
   - **developer** × N（2〜5名、Plan approval 有効）
     - プロンプト: 担当スコープ要件、契約定義、所有ファイル一覧、テスト要件
   - **reviewer** × 1〜2（Plan approval 不要）
     - プロンプト: レビュー基準（正確性、可読性、シンプルさ、セキュリティ、パフォーマンス、テスト十分性）
3. 共有タスクリストにタスク作成（実装タスク → レビュータスクの依存関係を設定）
4. 開発者が並列で実装 → レビュアーがレビュー → 指摘は担当開発者にフィードバック → 修正 → 再レビュー

## フェーズ4: 統合と品質確認

1. 全タスク完了を待つ
2. 全体テスト実行
3. format/lint 実行
4. 統合問題があれば対処
5. 残りの変更をコミット

## フェーズ5: PR 作成

`impl-max` のフェーズ3と同じ手順で PR を作成する。

## フェーズ6: チーム解散

全チームメイトにシャットダウン要求 → チームリソースをクリーンアップ

## チームメイトの役割

| 役割 | 人数 | 責務 |
|------|------|------|
| developer | 2〜5 | 担当スコープの実装とテスト。所有ファイルのみ編集 |
| reviewer | 1〜2 | コードレビュー。指摘は重大度付きで報告 |

## ルール

- **リードは各スコープの実装を行わない。** 統合フェーズでの最小限の調整は許容
- 各開発者のファイル所有権は重複不可
- 契約定義は開発者スポーン前にコミット
- レビュー指摘は全重大度（🔴🟠🟡🟢）で修正
- 各開発者は担当スコープ完了時にコミット
- チームメイトがエラーで停止した場合、リードが再スポーンまたは対処する
- 共有タスクリストで進捗を管理する
