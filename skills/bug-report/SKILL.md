# bug-report

対話形式でバグの症状をヒアリングし、AIがコードベースを調査して構造化された GitHub Issue を作成するスキル。
技術的な知識がなくても、対話に答えるだけで適切なバグレポートが作成される。

## 引数

- **テキスト** (例: `/bug-report ログインできない`): テキストを初期情報として扱い、不足分をヒアリングする
- **引数なし**: 最初からヒアリングを開始する

## 実行プロセス

### フェーズ1: ヒアリング

対話形式でバグの情報を収集する。**平易な日本語で質問し、技術用語は使わない。**

#### ステップ1-1: 基本情報の収集

最初に以下の3点を `AskUserQuestion` でまとめて聞く。引数でテキストが提供されている場合は、すでにわかっている情報をスキップし、足りない情報のみ聞く。

1. **何が起きたか**: どんな問題が発生しているか
2. **どこで起きたか**: どの画面・機能・ページで発生したか
3. **エラーメッセージ**: 画面やコンソールにエラーメッセージが表示されていたか（スクリーンショットがあれば貼ってもらう）

#### ステップ1-2: 状況に応じた追加質問

ステップ1-1の回答内容に応じて、**必要な情報だけ**を追加で聞く。すべてを聞く必要はない。

| 状況 | 追加で聞くこと |
|------|-------------|
| エラーメッセージあり | エラーの詳細、スクリーンショットの依頼 |
| 再現条件が不明 | 毎回起きるか、特定の条件でのみか |
| 画面・UIの問題 | ブラウザ、デバイス、画面サイズ |
| データに関する問題 | 特定のデータ・アカウントでのみ起きるか |
| タイミングの問題 | いつから起きているか、直前に何か変更したか |
| 操作手順が不明確 | 具体的な操作手順（1つずつ確認） |

**注意:**
- 1回の追加質問で聞くのは最大3つまで
- 回答から推測できる情報は聞かない
- 十分な情報が得られたら追加質問を切り上げる

### フェーズ2: コードベース調査

ヒアリングで得た情報をもとに、AIがコードベースを調査する。

1. **関連コードの特定**
   - ヒアリング内容（画面名、機能名、エラーメッセージ等）をキーワードにして `Grep` / `Glob` で検索する
   - 必要に応じて `Explore` エージェントで広範な調査を行う

2. **原因箇所の推定**
   - エラーメッセージやスタックトレースがある場合はそこから追跡する
   - ユーザーが報告した画面・機能に対応するコードを読み、問題箇所を推定する
   - 推定には確度を明示する（確実 / 可能性が高い / 要調査）

3. **影響範囲の確認**
   - 同じコードを使っている他の機能への影響を確認する
   - 関連するテストがあれば確認する

4. **再現の試行**（テストやコマンドで再現可能な場合のみ）
   - 関連するテストを実行して失敗を確認する
   - テストがない場合はスキップする（テスト作成はしない）

### フェーズ3: 重複チェック

1. `gh issue list --state open --search "<バグの要約>"` で既存の Open Issue を検索する
2. 類似の Issue が見つかった場合：
   - ユーザーに「この問題はすでに報告されている可能性があります（#XX: タイトル）」と伝える
   - **重複の場合**: 既存 Issue にコメントを追加するか、新規作成するかをユーザーに確認する
   - **関連しているが別の問題の場合**: 新規 Issue を作成し、関連 Issue として言及する

### フェーズ4: Issue プレビューと確認

1. 収集した情報と調査結果をもとに Issue の下書きを作成する
2. **ユーザーに下書きをプレビュー表示する**
   - 技術的な内容（原因推定、関連コード）と、平易な説明の両方を含める
   - 「この内容で Issue を作成してよいですか？」と確認する
3. ユーザーが修正を求めた場合は修正する
4. 承認されたら次のフェーズに進む

### フェーズ5: GitHub Issue 作成

1. `gh issue create` で Issue を作成する
   - タイトル: `bug: <バグの要約>`
   - ラベル: `bug` を付与する（ラベルが存在する場合）
   - 本文: 下記のテンプレートに従う
2. 作成した Issue の URL をユーザーに報告する
3. 簡潔なサマリーを伝える

#### Issue テンプレート

```markdown
## バグ概要

<1-2行の要約>

## 症状

<何が起きているかを具体的に記述>

## 期待される動作

<本来どうあるべきか>

## 再現手順

1. <手順1>
2. <手順2>
3. ...

## 発生環境

- ブラウザ / デバイス: <該当する場合>
- 発生頻度: 常に / 時々 / 特定条件で
- 発生時期: <いつから>

## 原因箇所（推定）

> 確度: 確実 / 可能性が高い / 要調査

- `<ファイルパス>:<行番号>` — <推定される原因の説明>
- 関連ファイル:
  - `<ファイルパス>` — <関連する理由>

## 影響範囲

- 影響を受ける機能: <機能名>
- 他の機能への影響: あり / なし / 要確認

## 重大度

<下記の基準に基づいて判定>

## 補足情報

<エラーログ、スクリーンショット、スタックトレース等>
```

#### 重大度の基準

| 重大度 | 基準 | 例 |
|-------|------|-----|
| 🔴 Critical | サービス停止、データ損失、セキュリティリスク | ログインできない、データが消える |
| 🟠 High | 主要機能が使えない、回避策がない | 検索が動かない、保存できない |
| 🟡 Medium | 機能は使えるが不便、回避策あり | 表示が崩れる、動作が遅い |
| 🟢 Low | 軽微な問題、使用に支障なし | 誤字、色のずれ |

## ルール

- ヒアリングでは**技術用語を使わない**。ユーザーが使った場合のみ、同じ言葉で返す
- 質問は**最小限**に留める。回答から推測できることは聞かない
- コード調査は**推測ではなく実際のコードを確認**して行う
- 原因推定の確度は正直に示す。わからない場合は「要調査」とする
- Issue を作成する前に**必ずプレビューを表示してユーザーの承認を得る**
- 勝手にコードを修正しない。このスキルの成果物は Issue のみ
- 修正が必要な場合は Issue 作成後に `/bug-fix #<Issue番号>` を案内する
