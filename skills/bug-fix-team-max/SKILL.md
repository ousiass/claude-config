# bug-fix-team-max

複数の調査者がバグの原因仮説を並列で検証する「科学的討論」方式で根本原因を特定する。

> **注意**: Agent Teams を使用するため `bug-fix-max` より多くのトークンを消費する。原因が明白なバグや仮説が1つの場合は `bug-fix-max` を推奨。

## 前提条件

- Claude Code 環境
- `git`, `gh` CLI

## 引数

`bug-fix-max` と同じ:
- **Issue 番号** / **Issue URL** / **テキスト** / **引数なし**

## フェーズ1: バグ報告の整理

`bug-fix-max` のフェーズ1と同じ手順でバグ情報を整理しブランチを作成する。

## フェーズ2: 仮説立案

1. バグの症状に関連するコードを調査する
2. 根本原因の仮説を2〜5個立てる（各仮説は独立して検証可能、調査コード領域を添える）

## フェーズ3: チーム編成と並列調査

1. エージェントチームを作成する
2. **investigator** × N（仮説ごとに1名、2〜5名）をスポーン
   - **読み取り専用**（コード変更不可）
   - プロンプトに含める: 担当仮説、調査コード領域、症状・再現手順、他の調査者一覧と仮説（相互反論のため）
3. 共有タスクリストに仮説ごとの調査タスクを作成
4. 調査者同士がメッセージで発見を共有し、互いの仮説を検証・反論する

## フェーズ4: 原因の合意形成とチーム解散

1. 全調査者の結果を収集
2. 最も有力な根本原因を特定
3. 全調査者にシャットダウン要求 → チームリソースをクリーンアップ
4. 根本原因と修正方針をユーザーに報告し合意を得る

## フェーズ5: 修正サイクル

`bug-fix-max` のフェーズ3と同じ:
回帰テスト作成 → 修正 → テスト確認 → `review` エージェントでレビュー → format/lint → コミット

## フェーズ6: PR 作成

`bug-fix-max` のフェーズ4と同じ手順で PR を作成する。

## チームメイトの役割

| 役割 | 人数 | 責務 |
|------|------|------|
| investigator | 2〜5 | 担当仮説の検証。読み取り専用。他の調査者の仮説に積極的に反論する |

## ルール

- 調査者はコード変更不可。読み取り・分析のみ
- 各仮説は独立して検証可能であること
- 調査者は互いの発見を共有し積極的に反論すること
- 根本原因はユーザーの合意を得てから修正に着手
- 修正の前に必ず回帰テストを書く
- 修正は最小限。バグに無関係なリファクタリングを混ぜない
- チームメイトがエラーで停止した場合、リードが再スポーンまたは対処する
- 共有タスクリストで進捗を管理する
