# code-review-git

git リモートブランチとの差分（変更ファイル・変更行）を対象に、コード品質チェックとドキュメント乖離検出を行うスキル。
PR 作成前のセルフレビューや、マージ前の最終確認に最適。

## 引数

- 引数なし: 現在のブランチと `origin/develop` との差分を対象にする
- ブランチ指定: 比較先のリモートブランチを指定する（例: `origin/main`）

## 実行プロセス

### フェーズ1: 差分の取得と把握

1. リモートの最新情報を取得する（`git fetch origin`）
2. 比較元ブランチを決定する
   - 引数がある場合はそれを使用する
   - 引数なしの場合は `origin/develop` を使用する
3. マージベースを取得する（`git merge-base <比較元> HEAD`）
4. 差分のあるファイル一覧を取得する（`git diff --name-status <merge-base>...HEAD`）
5. 差分の統計を取得する（`git diff --stat <merge-base>...HEAD`）
6. コミット一覧を取得する（`git log --oneline <merge-base>..HEAD`）
7. 差分の規模と影響範囲を把握し、チェック対象を TodoWrite でタスク化する

### フェーズ2: コード品質チェック（変更差分のみ）

変更されたファイルの差分（`git diff <merge-base>...HEAD -- <ファイル>`）を取得し、**変更された箇所を中心に**チェックする。
ただし、変更箇所の周辺コンテキスト（関数全体、クラス全体）も必要に応じて読み取り、正確にレビューする。

#### チェック観点

| チェック項目 | 基準 |
|------------|------|
| **セキュリティ** | 変更箇所にセキュリティリスク（インジェクション、XSS、認証バイパス、シークレットのハードコード等）がないか |
| **バグリスク** | nil/null 参照、未チェックの戻り値、型変換の失敗、境界値の未考慮、競合状態など実行時エラーが発生しやすい変更がないか |
| **エラーハンドリング** | 新規・変更箇所のエラーが適切に処理されているか。握りつぶしや不適切な無視がないか |
| **ロジックの正確性** | 変更されたロジックが意図通りに動作するか。エッジケースは考慮されているか |
| **パフォーマンス** | 変更により N+1 クエリ、不要なループ、メモリリークのリスクが導入されていないか |
| **テスト** | 変更に対応するテストが追加・更新されているか。テストカバレッジが低下していないか |
| **命名・可読性** | 新しい変数名・関数名・クラス名が適切で一貫しているか |
| **重複コード** | 変更によって既存コードとの重複が発生していないか |
| **依存関係** | 新しい依存が追加されている場合、妥当か。不要な依存がないか |
| **一貫性** | 変更がプロジェクトの既存パターン・規約に沿っているか |
| **Linterly 設定の改変** | `.linterly.yml` のデフォルト値（max_lines_per_file: 300, max_lines_per_directory: 2000, warning_threshold: 10）が緩和されていないか。`.linterlyignore` に不要な除外パターンが追加されていないか。`lefthook.yml` から `linterly check` が削除されていないか |

#### 手順

1. 変更ファイルを種類ごとに分類する（ソースコード、テスト、設定、ドキュメント）
2. 各ソースコードファイルの差分を取得し、変更箇所を中心にチェックする
3. 変更箇所の周辺コンテキストが必要な場合はファイル全体を読む
4. テストファイルの変更がある場合はテストの妥当性もチェックする

### フェーズ3: ドキュメント乖離チェック（差分内のドキュメント変更 vs コード変更）

差分に含まれるドキュメントの変更と、差分に含まれるコードの変更の整合性をチェックする。
**両方とも差分から取得する。** プロジェクト全体のドキュメントを走査するのではなく、差分内の変更同士を突き合わせる。

#### 手順

1. 差分に含まれるファイルを分類する
   - **ドキュメント差分**: `.md`, `.rst`, `.txt` ファイルの変更内容（`git diff <merge-base>...HEAD -- <ドキュメントファイル>`）
   - **コード差分**: ソースコード、設定ファイルの変更内容（`git diff <merge-base>...HEAD -- <コードファイル>`）
2. コード差分から、ドキュメントへの反映が必要な変更を特定する
   - API / CLI のインターフェース変更（エンドポイント追加・変更、引数変更、レスポンス変更など）
   - 設定・環境変数の追加・変更・削除
   - ディレクトリ構成・ファイル構成の変更
   - 依存関係の追加・削除
   - 機能の追加・削除・変更
3. ドキュメント差分から、対応するコード変更があるべきものを特定する
   - ドキュメントに新機能の記述が追加されている → 対応する実装が差分にあるか
   - ドキュメントの手順が変更されている → 対応する設定やスクリプトの変更が差分にあるか
4. 両者を突き合わせて乖離を検出する
   - コード変更あり・ドキュメント更新なし → ドキュメントの更新漏れ
   - ドキュメント変更あり・コード変更なし → 先行するドキュメント更新（実装待ち）または不要な変更
   - 両方変更あり・内容が矛盾 → ドキュメントとコードの不一致

### フェーズ4: テスト実行

1. テストが実行可能な場合はテストを実行する
2. 変更に関連するテストが失敗していないか確認する
3. テスト結果をレポートに含める

### フェーズ5: レポート生成

1. `AskUserQuestion` で出力先をユーザーに確認する：
   - **GitHub Issue に作成**（推奨）: タイトルは `review: Git差分レビュー(<ブランチ名> → <比較先>, <YYYY-MM-DD>)` の形式
   - **ローカル MD ファイルに保存**: プロジェクトルートに `code-review-git-report.md` を生成する
2. 選択された出力先にレポートを出力する
3. レポートの要約をユーザーに報告する

#### 重大度の基準

| 重大度 | 基準 |
|-------|------|
| 🔴 重大 | セキュリティリスク、データ損失の可能性、本番障害に直結する問題、仕様と明確に矛盾するドキュメント |
| 🟠 重要 | バグリスク、アーキテクチャ違反、テスト不足、更新漏れのドキュメント |
| 🟡 提案 | 可読性・保守性の改善、リファクタリング候補、ドキュメントの補足・改善 |
| 🟢 軽微 | 命名の改善、コードスタイル、表記ゆれ |

## ルール

- **差分に集中する。** 変更されていないコードの品質問題は対象外（明らかなセキュリティリスクを除く）
- 推測で指摘しない。実際のコードと差分を確認して裏付けを取ること
- 指摘には必ず該当ファイルと行番号を示すこと
- 改善案は具体的に示す。「改善すべき」だけで終わらせない
- 変更箇所だけでなく、周辺コンテキスト（関数全体、呼び出し元など）も確認して正確にレビューする
- 🔴（重大）または🟠（重要）の指摘は必ずレポートに含める
- 🟡（提案）や🟢（軽微）は、明確なメリットがある場合のみレポートに含める
- プロジェクトの既存パターン・規約を尊重する。プロジェクトのスタイルに合わない指摘はしない
- ドキュメント乖離は差分内のドキュメント変更とコード変更の突き合わせのみ行う。差分に含まれないドキュメントは対象外
- 各フェーズの進捗は TodoWrite ツールで管理する
