# bug-fix-team

Agent Teams を活用し、複数の調査者がバグの原因仮説を並列で検証するスキル。調査者同士が互いの仮説に反論する「科学的討論」方式で、根本原因を効率的に特定する。

> **注意**: このスキルは Agent Teams を使用するため、通常の `bug-fix` スキルより多くのトークンを消費する。原因が明白なバグや仮説が1つしかない場合には `bug-fix` の使用を推奨する。

## 引数

`bug-fix` スキルと同じ:
- **Issue 番号** (例: `/bug-fix-team #42`): GitHub Issue からバグ報告を取得する。`gh issue view` で内容を読み取る
- **Issue URL** (例: `/bug-fix-team https://github.com/owner/repo/issues/42`): 同上
- **テキスト** (例: `/bug-fix-team ログイン時に500エラー`): テキストをそのままバグ報告として扱う
- **引数なし**: ユーザーにバグの症状をヒアリングしてから開始する

## 実行プロセス

### フェーズ1: バグ報告の整理

`bug-fix` スキルのフェーズ1と同じ手順でバグ情報を整理し、ブランチを作成する。

### フェーズ2: 仮説立案

1. バグの症状に関連するコードを調査する
2. 根本原因の仮説を2〜5個立てる
   - 各仮説は独立して検証可能であること
   - 仮説には調査すべきコード領域を添える

### フェーズ3: チーム編成と並列調査

1. エージェントチームを作成する
2. **investigator** × N（仮説ごとに1名。通常2〜5名）をスポーンする
   - 調査者は**読み取り専用**（コードを変更しない）
   - スポーンプロンプトに含める情報：
     - 担当する仮説の内容
     - 調査すべきコード領域
     - バグの症状と再現手順
     - 他の調査者の名前一覧（相互メッセージ用）
     - **他の調査者の仮説一覧と、それらに対して積極的に反論すること**
3. 共有タスクリストに仮説ごとの調査タスクを作成する
4. 調査者同士がメッセージで発見を共有し、互いの仮説を検証・反論する

### フェーズ4: 原因の合意形成とチーム解散

1. 全調査者の結果を収集する
2. 最も有力な根本原因を特定する
3. すべての調査者にシャットダウンを要求し、チームリソースをクリーンアップする
4. 根本原因と修正方針をユーザーに報告し、合意を得る

### フェーズ5: 修正サイクル

`bug-fix` スキルのフェーズ3と同じ手順で修正する：
1. 回帰テストを作成する（修正前に失敗することを確認）
2. 最小限の修正を実装する
3. テストがパスすることを確認する
4. レビューを行い、指摘があれば修正する
5. format / lint を実行する
6. コミットする

### フェーズ6: PR 作成

`bug-fix` スキルのフェーズ4と同じ手順で PR を作成する。

## チームメイトの役割

| 役割 | 人数 | 責務 |
|------|------|------|
| investigator | 2〜5 | 担当仮説の検証。読み取り専用で調査し、他の調査者の仮説にも反論する |

## ルール

- 調査者はコードを変更してはならない。読み取り・分析のみ
- 各仮説は独立して検証可能であること
- 調査者は互いの発見を共有し、積極的に反論すること
- 根本原因はユーザーの合意を得てから修正に着手すること
- 修正の前に必ず回帰テストを書くこと
- 修正は最小限に留め、バグに無関係なリファクタリングを混ぜない
- チームメイトがエラーで停止した場合、リードが確認し再スポーンまたは対処する
- 各フェーズの進捗は共有タスクリストで管理する
